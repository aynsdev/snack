Projects shipped 2026-08-05 as the section replacing the rail's "Tasks — coming soon". Boards, sprints, backlog, customizable cards, and assignment scoped to project members. The design calls worth knowing before touching it:

**A card has two independent placements, and collapsing them breaks the sprint rollover.** `tasks.board_column_id` is *status* and is never null; `tasks.sprint_id` is *when*, and null means the backlog. The obvious shortcut — "the backlog is a column" — fails the moment a sprint ends: unfinished work has to return to the backlog **keeping the status it reached**, and a column-only model has already thrown that away. Browser-verified: a card that got to "In progress" comes back to the backlog still In progress.

**Task numbers come from `projects.next_task_number`, never `MAX(number)+1`.** Deleting the newest task would otherwise hand its number to the next one created, and PWA-1499 meaning two different things is worse than a gap. Allocated with one `UPDATE … RETURNING` so two simultaneous files get different numbers.

**Positions are sparse (`App\Support\Positions`, gap 65536) and a drop writes exactly one row.** Renumbering the column on every drag makes two concurrent drags a lost update. The client sends neighbour *ids*, never positions — a client sending positions is sending a copy of a board it painted seconds ago. When a seam runs out of integers, that one list is spread again and the move retried.

**`project_members` is what makes somebody assignable.** Reading a board is open to the whole workspace (guests excepted); working it needs membership — `ProjectPolicy::view` vs `::contribute`, the same preview/post split channels make. An assignee who is not a member is silently dropped to null rather than refused, because it is reachable by removing somebody in one tab while their name sits on a card in another.

**Column names are free text; `ColumnCategory` (unstarted/started/done) is what the application reasons about.** Nothing may infer status from a name — the reference board had "To fix" between testing and releasing. Two rules depend on the category, so a board must keep at least one column of each: where new work lands, and what counts as finished when a sprint closes.

**Customizable cards = `projects.card_fields` (jsonb display toggles) + per-project labels.** Read through `Project::cardFields()`, which fills in defaults for keys a project predates — so a toggle added later is not frozen off for every existing project. `TaskType` stays a fixed enum because the app reasons about it (only Epics contain, one level deep).

Also: `Workspace::tasks()` is a HasManyThrough that exists *for the route binding* — `tasks/{task}` is inside `scopeBindings()`, so a cross-tenant id 404s at the router. Assignment raises a `task_assigned` notification, the first `NotificationReason` that is not about a message; it has no container, so `notification-row.tsx` renders the project name and builds its own `?task=PWA-1` link (rendering ContainerLabel there read "Unknown" — found in the browser, fixed).

Drag and drop is native HTML5, no new dependency. See [[snack-phase-status]] and [[snack-container-abstraction]].

**A sprint project between sprints has no board, and that had to be said out loud (fixed 2026-08-07).** `uses_sprints` defaults to true and nothing creates a sprint, so every new project opened on three empty columns whose Create buttons filed cards with `sprint_id: null` — visible until the next reload, then apparently gone. Reported as "my tasks disappear when I move them". The columns are now replaced by a panel (`WaitingForSprint` in `pages/projects/board.tsx`) rather than left empty, because an empty board over cards in the database is the one state a reader cannot tell apart from a broken one. The invariant to keep: **no control may file work where the surface it was filed on cannot show it.** `backlogCount` is a board prop computed only when there is no active sprint, so an ordinary load does not pay for the count.

**Releases shipped 2026-08-07 as the project's third view** — tabs are now Backlog, Board, Releases, Settings, in the order work moves through them. A release is *what ships* where a sprint is *when a team works*: `tasks.release_id` is a third independent placement beside `sprint_id` and `board_column_id`, `nullOnDelete` so cancelling a release unschedules the work instead of deleting it. Name is citext-unique per project. Scheduling goes through `PATCH tasks/{task}` with `release_id` from both the card panel and the release page — deliberately no release-owned attach endpoint, so there is one authorization path. Every place a card is serialized must eager-load `release` (TaskController ×3, TaskMoveController, TaskChanged, `Task::scopeWithCardData`) — missing one shows a null release in the panel with no error.

**The releases UI is Jira-shaped (rebuilt same day, from the user's screenshot): an index *table* plus a detail page.** The table is Release · Status · Progress · Start date · Release date · Description · ⋯, with a search box and a Released/Unreleased filter applied client-side (tens of rows, all already on the page). The index sends **counts, not contents** — `withCount(['tasks', 'tasks as completed_tasks_count' => …whereNotNull('completed_at')])` — because a bar per row must not cost a board-sized payload per row; the cards come only with `projects.releases.show`. Status is derived from `releases.released_at` via `ReleaseState`, no status column, and **overdue means "the day passed and it has not gone out"** — deliberately not "has unfinished work", so a version whose cards are all done but which nobody released still reads as late, and one that shipped with things cut does not. Release/unrelease is its own endpoint pair (`…/releases/{release}/released` POST/DELETE) like channel archiving; `markReleased()` keeps the first timestamp so a double click cannot move the recorded date.

**Starred projects, and the sidebar heading that was hiding (2026-08-07).** A star is a fact about the *viewer*, so it is `project_members.starred_at` — the sidebar already loads that row for the viewer on every page, so starring costs no extra query and needs no second table. A timestamp, not a flag, because the starred list is ordered by it and a double-tapped star must therefore not rewrite it (the store endpoint is idempotent). Gated on membership, not on managing the project: it changes nothing anybody else can see. Starred projects are *lifted out* of their group in the sidebar rather than repeated above it, and a heading left with nothing under it is dropped.

The reported bug in the same area: the sidebar hid a group heading whenever there was only one section (`sections.length > 1`). That rule was written for the synthetic "Ungrouped" label but also swallowed a real one, so a user with a single project filed under "Development" saw a bare list. **A named group always names itself; only "Ungrouped" is suppressed when it stands alone.**

**Summary is the project's first tab (2026-08-07)** — Summary · Backlog · Board · Releases · Settings. `ProjectSummaryController` answers it with aggregates only: one conditional-count query for the four 7-day tiles, one grouped query each for status/priority/type, and eight rows for the activity list. Nothing serializes a card to draw a bar. Two rules baked in: **every column and every enum level is returned even at zero**, so the chart's shape doesn't change with what happens to be in use that week; and the activity list is *cards recently touched*, not a field-by-field history — none is stored, and inventing "Alicia changed the assignee" from an `updated_at` would be a story rather than a record.

Charts are plain divs (no charting dependency) over one **sequential ramp**, `--viz-ramp-from`/`--viz-ramp-to` in `app.css`, with separate steps per surface — deliberately blue, not the brand orange, because an orange bar beside orange buttons reads as clickable and the accent is re-themed per workspace. Both ends were measured (≥3:1 against their surface; lightness monotone — the categorical validator is *meant* to fail on a sequential ramp). Segments mix between the ends in oklab so any column count gets an even ramp. The one non-obvious bug caught in the render pass: **the ramp step must come from the index in the full list, not among the non-empty ones**, or the legend swatch and the bar disagree about the same status and filing one card into an empty column repaints the chart.

**A board's shape is edited on the board, not in settings (2026-08-07).** The whole "Board columns" section is gone from project settings and the page no longer receives a `columns` prop. Renaming is clicking the column's own name in the header; the rest moved into a per-column ⋯ menu (category, WIP limit, delete). The trap that cost time: **a field inside a Radix dropdown cannot save on blur** — closing the menu unmounts the input and an unmounted field does not blur, so the value is lost by the gesture that means "done". The limit is therefore committed from `onOpenChange(false)`, which fires for Escape, click-away and item selection but *not* for `setOpen(false)` called by our own code — Radix only reports the state changes it makes itself.

**Columns can be added from the board (2026-08-07).** The `+` is a small square at the far *right* of the strip, Jira-style, but `SaveBoardColumn::create()` now takes `before_column_id`/`after_column_id` and the board sends the seam left of the first Done column — a status added mid-flow is another step before finished, and one landing right of Done reads backwards. Called with neither id it still appends, which is what the settings screen does.

**`projects.next_task_number` is editable in project settings (2026-08-07)** so a team arriving from another tracker can carry its numbering on. It only moves forward — `UpdateProjectRequest::after()` refuses anything at or below `MAX(tasks.number)`, because `(project_id, number)` is unique and a counter wound back does not fail at the setting, it fails weeks later on somebody's ordinary click.

**The card panel grew a Development block, comments, and files (2026-08-07).** Snack fronts no repository and does not pretend to: Development hands over three strings — the branch, `git checkout -b …`, and a commit message carrying the reference. The name is composed server-side in `App\Support\BranchName` (`feature|bugfix|epic` from the type, then the reference, then a slugged title cut at a word boundary, capped at 48 chars) and travels on `TaskResource.branch_name`, so every surface offers the same one; slugging is also what makes it a legal git ref by construction rather than by an escape list. The trap worth remembering: **on plain HTTP `navigator.clipboard` is undefined**, so two of the three buttons would have silently done nothing in this project's own dev environment — there is a local `execCommand('copy')` fallback in `development-section.tsx`, browser-verified on snack.test. See [[snack-insecure-context-apis]].

Comments are `task_comments`, deliberately *not* messages: a channel message is addressed to a room and scrolls away, this is addressed to the card and has to still read months later — and folding them into `messages` would grow a "…and not a task comment" clause in every timeline query, search filter and unread count. Plain text (no composer markers — there is no parser behind them), `author_id` nullOnDelete so a deleted account leaves its reasoning behind, and `edited_at` separate from `updated_at` because it is what the "(edited)" mark means. **Editing is the author's alone, not even a lead's** — an edit by a third party is the record ceasing to be true while still carrying the original name — while deleting is the author's or a lead's, the same split as deleting a card.

Files on a card reuse `message_attachments` with a nullable `task_id` rather than a second table: the private-disk key, the detected mime type, the queued thumbnail and the signed re-authorizing download route are identical, and a copy of that apparatus is the copy that misses the next security fix. A DB check constraint keeps at most one owner, because "who may read this file" must not have two answers; `DownloadController` gained one branch (a card's file is read by whoever may read its project). **The trap: `scopeOrphaned()` and the `message_attachments_orphaned_index` meant "no message", so `snack:prune-uploads` would have deleted every card's file within a day.** Both now require `task_id IS NULL` too, and a test asserts it. Unlike the composer there is no tray: the card exists when the file is chosen, so upload *is* attach, in one request.

Both arrive only from `tasks.show` (`whenLoaded`), fetched by `useTaskDetail` when a panel opens — a board is eighty cards and eighty discussions is a payload nobody reads.

**The board has a Jira-style filter bar (2026-08-07)**: search, member avatars, Version, Type, and a Quick filters menu, all applied client-side by `filterTasks` over the cards the board already holds — narrowing must not cost a round trip, and there is no Apply button because there is no request to wait for. Two rules: the **column counts follow the filter** (a count that ignored it would describe a board nobody is looking at), and **drags still compute their neighbours against the whole list**, so dropping between two cards a filter has hidden cannot reorder the board. Filter state is component state, not the URL — a filtered board is a way of looking at one, not a place, and a query string would put every keystroke into browser history.

**Project groups (2026-08-06) are headings, not containers.** `project_groups` is workspace-scoped with a citext-unique name; `projects.project_group_id` is nullable and `nullOnDelete`, so deleting a group ungroups its projects and destroys nothing — that is why delete needs no confirmation. Ungrouped is the absence of a group, not a second state: assignment is one endpoint taking `project_group_id: id|null`. Two rights, deliberately split — curating groups is `canCreateProjects()` (a member's right, guests excluded), but moving a project between them is `update` on *that project*, because it changes somebody else's project. Order is a sparse `position` and a move **swaps with the neighbour** (two rows) rather than renumbering, for the concurrency reason positions are sparse everywhere here.

The sidebar shows the same headings, but **only the groups holding one of your projects** — `WorkspaceNavigator::sidebarProjectGroups()` derives them from the eager-loaded `group` relation on the projects already fetched, so no extra query and no empty heading in the narrowest column in the app. A single unheaded section stays a flat list; the project page is the opposite, keeping empty groups visible because that is where they are curated.

**Reported 2026-08-07 as "6 projects in the group, 5 in the sidebar" — not a bug in the counts, a missing door.** The list page counts every project in the workspace; the sidebar counts the ones you are a *member* of (`WorkspaceNavigator::memberProjects()` → `whereMember`). The genuine defect behind it: `projects.membership.store`/`destroy` existed, were policy-gated and tested, and **nothing in the UI ever called them** — so a project you were not on could never reach your sidebar. The board's own banner even read "Join the project to file and move work on it" with nothing to press. Fixed by adding `join`/`leave` to `ProjectResource.abilities` (both read the membership row already eager-loaded for the viewer, so they cost no query) and rendering the controls in the project card's ⋯ menu and that banner. The lesson worth keeping: **an endpoint with tests and no call site is invisible work** — when a payload deliberately shows a subset, something on the screen has to explain the subset and offer the way across.

Writing the query-count guard for that list exposed a **pre-existing N+1**: `ProjectResource` asks `ProjectPolicy`, which reads `$project->workspace` — a lazy load per project, doubled because the index page and the shared sidebar payload hold separate instances (30 projects cost 54 extra queries). Fixed the way `MessageHistory::shareContainer()` does it: `setRelation('workspace', $workspace)` on each row in both `ProjectController::index()` and `WorkspaceNavigator::memberProjects()`. Any future list of projects needs the same line.

Two things that only showed up in the browser: assignment could not ride on `projects.update` (that redirects to project settings, and the move is done from the *list*), hence `PATCH projects/{project}/group` returning `back()`; and `DropdownMenuItem variant="destructive"` paints `--destructive-foreground`, which is near-black in this theme — the delete item read as disabled until it was styled `text-destructive` instead.
